## 1. Original Context

Jira EPMCDME-14725 — "Fix UI issues with interactive components generated by LLM" (Bug, Major, labels Frontend / codemie_core)

## Summary
Interactive components generated by the LLM are displayed with UI issues in the CodeMie conversation/share preview experience.

## Description
When the LLM generates interactive components in a CodeMie conversation, the resulting UI does not render or behave correctly. This affects the quality of the generated output experience and may prevent users from reliably interacting with assistant-generated components.
Reference conversation: https://codemie-preview.lab.epam.com/share/conversations/wEvSU7r19il1
The issue should be investigated and fixed so that interactive components generated by the LLM are rendered consistently, remain usable, and do not break the surrounding chat/conversation layout.

## Steps to Reproduce
1. Open the shared CodeMie Preview conversation link above.
2. Locate the message where the LLM generated interactive components.
3. Review the rendered UI of the generated interactive components.
4. Try to interact with the generated components where applicable.
5. Observe visual, layout, or interaction issues in the generated component UI.

## Expected Result
- LLM-generated interactive components are rendered correctly in the conversation/share preview.
- Components are visually aligned with the CodeMie UI design system.
- Interactive elements remain usable and accessible.
- Generated components do not overlap, overflow, break layout, or interfere with surrounding chat content.
- The same generated component output is displayed consistently after page reload and in the shared conversation view.

## Actual Result
- LLM-generated interactive components have UI issues in the conversation/share preview.

## Acceptance Criteria
1. LLM-generated interactive components from the referenced conversation render correctly in CodeMie Preview.
2. Interactive elements are visually aligned, readable, and usable.
3. Generated components do not overlap, overflow, truncate important content, or break the surrounding chat layout.
4. Component behavior remains stable after page reload.
5. Shared conversation preview displays the same corrected component UI as the original conversation view.
6. The fix is verified in supported browsers, at minimum Chrome and Edge.
7. No regression is introduced for regular chat messages, Markdown rendering, or existing chat action controls.

### Integration Points

**Where the LLM block is detected and parsed** — importantly, there is **no fenced-code-block or remark/rehype mechanism**; no ` ```a2ui ` detection exists anywhere.

- **Live stream**: `store/chatGeneration.ts` `_handleChunk` — SSE JSON chunks with an `a2ui` field are pushed onto `historyItem.a2uiEnvelopes` in arrival order; text chunks go to `historyItem.stream`. Envelopes and markdown are **two separate channels on one message**.
- **Reload / persisted**: `transformHistoryGroup` in `utils/chatHelpers.ts:162` copies `a2uiEnvelopes` (and the user turn's `a2uiAction` / `a2uiDataModel`) straight from the API payload.
- **Interpretation**: envelopes → `normalizeToCatalog(toPlainJson(envelopes))` → SDK `MessageProcessor.processMessages`. A pre-filter (`findUnsupportedComponentType`) diverts unknown component types to `A2uiFallback` before the SDK prints its own inline error.

Registry mapping: `registry.tsx` takes the SDK's 18-component `reactBasicCatalog.components` map and overrides six via `OWN_COMPONENTS`; non-overridden components get `withAccessibility(...)`, plus `withValidationMessage` for `ChoicePicker`/`Slider` (the SDK swallows validation text there). `createA2uiCatalog()` wraps the result as an SDK `Catalog(CATALOG_ID, components, BASIC_FUNCTIONS)`.

**Normal chat path**:
`ChatPage` → `ChatContext.Provider (isSharedPage:false)` → `ChatHistory` → `ChatHistoryGroup` → `ChatAiMessage` → Thoughts, `Markdown`, then `ChatA2uiBlock` → `useA2uiSurface` → `<div className="a2ui-scope mt-4 mb-3 flex flex-col gap-3">` → `A2uiErrorBoundary` → per-surface `<fieldset className={cn('contents', !isActive && 'pointer-events-none')}>` → `A2uiSubmittedActionProvider` → `A2uiModalTriggerProvider` → SDK `A2uiSurface` → registry implementations → `renderers.tsx`. Then `ChatAiMessageActions` (hidden when shared).

**Shared conversation path** (`/share/conversations/:token`, `router.tsx:122`):
`SharedChatPage.tsx` → `chatsStore.getSharedChat(token)` (`store/chats.ts:268`, GET `v1/share/conversations/{token}` → `transformChatBEtoFE` → `setOpenChat(chat, false)`) → `PageLayout` → `ChatContext.Provider` with a **stub value** → the **same** `ChatHistory` and identical component chain including `ChatA2uiBlock`.

Concrete differences between the two paths:

1. The shared context is built via `as unknown as ChatContextValue` supplying only `openConfigForm`, `isSharedPage: true`, `canAttachFiles: true`, `hideToolOutputs: false`, `setHideToolOutputs`. Everything else (`selectedAssistant`, `dynamicToolsConfig`, `selectedSkills`, `chatConfiguration`) is `undefined` — any consumer destructuring more can misbehave or throw.
2. **`ChatA2uiBlock` never reads `isSharedPage`.** On the shared page an unanswered surface on the last turn still computes `isSurfaceActive === true` (`!isChatBusy && !isSubmitting && !answers.has(id) && isAtEdge`), so it renders **fully interactive**, and a click calls `chatGenerationStore.submitA2uiAction` against a conversation the viewer cannot write to. This is the strongest candidate for the "not usable / not identical in shared view" half of the defect.
3. Layout wrapper differs: shared wraps `ChatHistory` in `PageLayout ... childrenClassName="px-0"` + `flex flex-col h-full`; the chat page has its own layout and sidebars, so effective surface width differs between views.
4. No prompt/composer in shared view, so surfaces sit at the very bottom of the scroll container.
5. The shared payload comes from a different endpoint. If the backend share serializer omits `a2uiEnvelopes` / `a2uiAction` / `a2uiDataModel`, the shared view silently renders nothing or an unanswered form — **must be verified against the actual API response** for the reference conversation.

### Patterns and Conventions

- Strict import discipline: only `a2ui/config.ts` names `@a2ui/*` versioned paths.
- SDK-first with documented exceptions — `registry.tsx:61-81` records each of the six overrides and why.
- Fail-soft everywhere: unsupported component → `A2uiFallback`; processor throw → fallback; render crash → `A2uiErrorBoundary`; bad media URL → `A2uiMediaPlaceholder`; invalid regexp → ignored.
- JSON-string memo keys (`prefillKey`, `submittedActionKey`) to get stable identities out of valtio proxies.
- Latest-handler refs (`handlerRef`, `actionHandlerRef`) so handler identity never retriggers surface replay.
- Normalization happens **before** the renderer sees envelopes, never patched inside a component.
- Every backend-advertised property must have an observable renderer effect, each pinned by a test.
- Heavy explanatory block comments instead of TODO/HACK markers (zero such markers in `src/a2ui/**`).

### Architectural Decisions

- Protocol is A2UI v0.9.1 Basic Catalog (18 components), one static `catalogId`; published catalogs are immutable — a composition change means a new id.
- The catalog's own components draw the surface; re-implementation is minimized.
- Exactly six components are ours, each with a recorded reason: Image/Video/AudioPlayer/Icon (URL sanitization, consent, own artwork), Button (Modal trigger must not dispatch), DateTimeInput (product picker).
- **Theming decision, most relevant to this bug**: catalog CSS custom properties cascade to 12 base vars mapped in `theme.css`. Layout CSS is supplied by us **because the published `@a2ui/react` build ships CSS-module class maps that are empty** — elements render `class="undefined"`, so the packaged rules cannot match. Our styling is written against a **pinned SDK version's markup** and must be re-checked on any SDK upgrade. The migration spec itself flags this as the most fragile area.
- Two catalog properties are supplied by us: `accessibility` (ARIA) and `validationRegexp` (blocks submission). Three gaps deliberately accepted and pinned by tests: number variant submits text, `validationRegexp` shows no field-level message, dialog carries no `role="dialog"`.
- Client checks are UX only, never a security boundary; the server re-validates every answer.
- Surface states: active / submitted / stale / busy. Answering is a regular chat request (`action` envelope + `a2uiDataModel`), no dedicated endpoint, no resume.
- Envelopes are persisted raw in JSONB and **replayed through the renderer on reload** — no server session state. This is the mechanism behind AC-4 (stability after reload).
- BE/FE sync: `npm run a2ui:manifest` regenerates `a2ui-manifest.json` (a FE test fails if skipped); the file is hand-copied into the backend. Invariant BE catalog ⊆ FE registry; rollout order frontend first, backend second.

## 6. Risk Indicators

**Styling fragility (primary suspect)**

- `src/a2ui/theme.css` supplies layout **by structural selectors on unversioned SDK markup**, because the published `@a2ui/react` build ships empty CSS-module class maps (elements render `class="undefined"`). Selectors include `.a2ui-scope label[for]`, `.a2ui-scope input + label[for]`, `.a2ui-scope strong + div`, `.a2ui-scope div:has(> .chip)`, `.a2ui-scope input… + span` (validation text by adjacency). Any SDK markup change silently breaks spacing and causes overlap. The file's own comment says it is pinned to a specific SDK version.
- Version drift: protocol/catalog pinned to `v0_9` while installed packages are `@a2ui/react@0.10.2` / `@a2ui/web_core@0.10.6`. If the `/v0_9` subpath markup shifted between package releases, the structural selectors are already stale — **verify this first**.
- Modal styling `.a2ui-scope + .a2ui-modal-overlay, .a2ui-modal-overlay > div` (`theme.css:302`) uses an adjacent-sibling selector. If the SDK portals the overlay to `document.body`, it matches neither the sibling rule nor the `.a2ui-scope` variable scope, leaving the dialog unstyled and untokenized.
- `.a2ui-own` opt-out is inconsistently applied: several rules do **not** exclude `.a2ui-own *` — `.a2ui-scope strong`, `input::placeholder`, `input[type=radio|checkbox]`, `.chip*`, `input[type='range']` — so theme CSS leaks into our own renderers.
- `theme.css` conflicts with `.ai-run/guides/styling/styling-guide.md` ("Tailwind only, no custom CSS"); the fix must justify staying in raw CSS.

**Layout and overflow**

- `ChatHistory.tsx` inner content is `flex flex-col gap-6 grow max-w-5xl mx-auto px-0.5` with the outer container `overflow-hidden` and **no `overflow-x-auto` anywhere on the AI side** — a wide Row/Card overflows horizontally with no escape.
- `ChatAiMessage.tsx` has `min-w-0` on its wrappers, but the a2ui subtree has **no `min-w-0` / `max-w-full`**, so flex children inside `A2uiSurface` can refuse to shrink.
- `ChatA2uiBlock.tsx:236` renders each surface as `<fieldset className={cn('contents', !isActive && 'pointer-events-none')}>`. `display: contents` on a `fieldset` is a known cross-browser inconsistency point and removes the box, so disabled styling and containment are never painted; read-only state is conveyed only by `pointer-events-none` plus `.a2ui-answered`.
- `renderers.tsx` uses fixed non-viewport-relative image widths (`max-w-40`, `max-w-80`, `max-w-[480px]`, `w-full max-h-64`), so a `largeFeature` image can exceed a narrow bubble.
- `main.scss` hides scrollbars globally except `textarea` / `.show-scroll` (WebKit `::-webkit-scrollbar { display:none }` plus a Firefox rule) — scrollable a2ui containers get invisible scrollbars in Chrome and Edge, which reads as truncated content.
- Font mismatch: `--font-family-body-sans` is applied only to `.markdown`, and `.a2ui-scope` sets `font-family: inherit`, so custom-appearance fonts never reach a2ui surfaces — prose and interactive block render in different typefaces (AC-2 "visually aligned").

**Shared preview**

- `ChatA2uiBlock` never reads `isSharedPage`, so an unanswered surface on the last turn renders fully interactive in the read-only share view and its submit calls `submitA2uiAction` against a conversation the viewer cannot write to. Directly violates AC-5 and the "remain usable" expectation.
- `SharedChatPage.tsx` builds `ChatContext` via `as unknown as ChatContextValue` with most fields `undefined` — a type-unsafe stub that will not fail at compile time if a consumer starts reading a new field.
- Unverified: whether the share endpoint (`v1/share/conversations/{token}`) actually serializes `a2uiEnvelopes` / `a2uiAction` / `a2uiDataModel`. If not, the shared view silently renders nothing or a permanently unanswered form. **This is a backend-dependency risk that could move the fix out of this repo.**

**Testing and verification**

- `SharedChatPage.tsx` has zero tests, and no test anywhere asserts read-only a2ui rendering in shared mode.
- No layout assertions exist for a2ui containers; jsdom cannot compute layout, so AC-1/2/3 (visual) and AC-6 (Chrome+Edge) are **not machine-verifiable in this repo** — they need manual browser verification or the external `codemie-test-harness`.
- `ChatA2uiBlock` tests mock `Markdown` entirely, so the markdown ↔ a2ui coexistence that AC-7 protects is untested.
- No coverage thresholds are enforced, so regressions in these files will not fail CI on coverage.
- Reproduction depends on an external preview environment (`codemie-preview.lab.epam.com/share/conversations/wEvSU7r19il1`); the ticket does not enumerate the concrete visual defects, so the actual failure set must be established empirically before scoping.

**Process and documentation**

- `.ai-run/guides/` has no a2ui/interactive-component guide at all; `error-handling-patterns.md:23,241` still references the deleted `src/components/InteractiveElements/InteractiveErrorBoundary.tsx`.
- Any catalog/registry change requires `npm run a2ui:manifest` plus a hand-copy into the backend, with rollout order frontend-first — an easy step to miss if the fix touches `SUPPORTED_COMPONENTS`.
- Requirements clarity risk: the ticket describes symptoms generically ("UI issues") without naming a single concrete defect, so acceptance is subjective until the defect list is pinned down.

## 7. Summary for Complexity Assessment

This task touches a narrow but deep slice of the frontend: the `src/a2ui/` module (protocol boundary, registry, renderers, and the hand-written `theme.css`), the single chat↔a2ui seam `ChatA2uiBlock.tsx`, its parent `ChatAiMessage.tsx`, the `ChatHistory` layout container, and `SharedChatPage.tsx`. There is no backend work in this repo, though there is an unresolved backend dependency: it is not yet confirmed that the share endpoint serializes a2ui fields at all. Realistic change surface is roughly **4–8 files**, concentrated in `theme.css`, `renderers.tsx`, `ChatA2uiBlock.tsx`, and `SharedChatPage.tsx`, plus new tests. The architecture is unusually well factored — one SDK boundary file, one mount point, one styling file — so changes are localized and low-blast-radius, which pulls complexity down.

Technical novelty is **low in structure but high in diagnosis**. The patterns are established and documented in the EPMCDME-13910 migration spec, and no new architecture is needed. The difficulty is that the ticket names no concrete defect, and the most likely root cause is inherently brittle: `theme.css` re-implements catalog layout using structural CSS selectors against unversioned SDK markup, a design the team adopted only because the published `@a2ui/react` build ships empty CSS-module class maps. Compounding this, the protocol is pinned to `v0_9` while the installed packages are 0.10.x, so the selectors may already be stale. Two further defects are visible from static reading alone and are likely part of the reported symptoms: `ChatA2uiBlock` never consults `isSharedPage`, so surfaces render fully interactive in the read-only share view; and there is no horizontal overflow escape anywhere on the AI message side while the a2ui subtree lacks `min-w-0`/`max-w-full`. Expect an investigation-heavy phase before a small, surgical change.

Test coverage posture is **mixed and specifically weak where this task lands**. The a2ui module has 16 test files and `ChatA2uiBlock.test.tsx` alone runs ~30 cases, so behaviour and wiring are well guarded. But `SharedChatPage.tsx` has zero tests, no test asserts read-only a2ui rendering in shared mode, `theme.css` and the container renderers are untested, and `ChatA2uiBlock` tests mock `Markdown` entirely, so the markdown↔a2ui coexistence protected by AC-7 is unverified. Critically, jsdom computes no layout and the repo has no in-repo e2e, so the visual acceptance criteria (AC-1, 2, 3) and the Chrome+Edge matrix (AC-6) **cannot be verified by automated tests here** — they need manual browser verification or the external `codemie-test-harness`. Key factors that should raise the complexity score: the undefined defect list requiring empirical reproduction against an external preview environment, the SDK version-drift question, the unresolved backend share-serialization dependency, and the fact that the primary suspect file conflicts with the repo's own "Tailwind only, no custom CSS" styling guide. Key factors that should lower it: excellent existing documentation, a single well-isolated integration seam, and strong behavioural test scaffolding to extend.
