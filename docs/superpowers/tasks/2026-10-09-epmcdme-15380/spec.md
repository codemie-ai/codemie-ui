# Spec: EPMCDME-15380 — Vertically scrollable global left navigation

## Problem

`src/components/Navigation/Navigation.tsx` renders the global left nav as a single
`<header id="navigation-menu">`. Its desktop branch (the `else` arm of the
`isMobileLayout ? [...] : [...]` className ternary, `h-full relative px-2 pt-6 pb-4 ...`) has no
`overflow-y` anywhere along its height chain. When logo + nav sections + pinned assistants + Help +
Profile + the expand/collapse button together exceed the viewport height, the excess is pushed
outside the header's `h-full` box with nothing to scroll it back into view. Help, Profile, and
"Hide Menu" become unreachable at reduced viewport heights, and the only workaround (reducing
browser zoom) is explicitly called out in the ticket as unacceptable.

The mobile branch of this exact same `<header>` (`MOBILE_OVERLAY_CLASS_NAME`) already carries
`overflow-y-auto` and does not exhibit the bug.

**Second, related symptom (confirmed by re-reading `NavigationPinnedSection.tsx` and
`Navigation.tsx:228-230`):** the pinned-assistants block (FAQ/Chatbot plus any user-pinned
assistants) sits inside a chain of three nested `flex-1 min-h-0` wrappers
(`Navigation.tsx:228-230`, the innermost also carrying `overflow-hidden`). `min-h-0` removes this
chain's content-based minimum size, so standard flexbox shrink distribution squeezes it toward zero
height first, before any sibling with an ordinary min-content floor (logo, Help, Profile, the
expand button — none of which opt out of their default minimum) is forced to overflow. The
component's own sizing logic (`NavigationPinnedSection.tsx:67,71-84`, a `ResizeObserver` on
`containerRef` feeding `availableHeight`) then computes `visibleSlots` from that height
(`NavigationPinnedSection.tsx:179-183`); once `availableHeight` reaches 0, `visibleSlots` is 0 and
the section renders no bubbles at all — it disappears completely rather than collapsing to an
overflow indicator, which is the behavior the user reported ("FAQ and Chatbot" vanishing).
Adding `overflow-y-auto` to the header alone does not fix this: flexbox resolves the shrink
distribution *before* any overflow is produced, so the min-h-0 chain still gets squeezed to zero
first and no overflow for the scrollbar to catch is ever generated by this section.

**Third, related constraint (raised on re-gate):** a fixed, unconditional height floor on that
wrapper would reserve empty vertical space in the already-tight reduced-viewport scenario this
ticket is about, whenever there happen to be zero pinned/help items to show (`NavigationPinnedSection`
already has exactly this empty state — it renders nothing when `helpAssistantsFetched &&
allItems.length > 0` is false, `NavigationPinnedSection.tsx:352`). The floor must therefore apply
only when there is at least one item to show, and must contribute zero height otherwise.

## Approach

> **Superseded.** The approach below (header-level `overflow-y-auto` plus a conditional height
> floor on the pinned-section wrapper) shipped first but was replaced in review by a different
> architecture: only the middle links section scrolls (`flex-1 min-h-0 overflow-y-auto` on that
> wrapper alone), while the logo, pinned section, Help, and Profile/expand button sit in
> non-shrinking, non-scrolling blocks. See `code-review-final.json` for what actually shipped and
> why. The problem statement and acceptance criteria above still hold; only this section is stale.

Changes to `Navigation.tsx`'s desktop branch:

1. **Make the desktop header scrollable** — add `overflow-y-auto overflow-x-hidden` to the
   desktop header className, mirroring the mobile branch's existing, working pattern.
   `overflow-x-hidden` guards against a horizontal scrollbar introduced by the vertical one's own
   width (precedented in `Sidebar.tsx:112`).

   **This was an open design fork, now settled by explicit user decision:** Profile and
   "Hide Menu" scroll away with the rest of the content rather than staying pinned/docked at the
   bottom (Option A, chosen over a non-scrolling-footer restructure).

2. **Give the pinned-assistants wrapper a conditional, non-zero height floor** — on the innermost
   `flex-1 min-h-0 overflow-hidden` wrapper around `NavigationPinnedSection`
   (`Navigation.tsx:230`), apply a minimum height (derived from the component's own
   `ITEM_HEIGHT`/`CONTAINER_PB` constants in `pinnedSectionUtils.ts:18-20`, e.g.
   `ITEM_HEIGHT + CONTAINER_PB` ≈ 54px, rounded up if padding/gap composition needs it) **only when
   there is at least one pinned/help item to show, and `min-h-0` (no floor, zero contributed
   height) otherwise.** The condition is the same one `NavigationPinnedSection.tsx:352` already
   uses (`helpAssistantsFetched && allItems.length > 0`) — reuse it rather than inventing a second
   one: `Navigation.tsx` reads the same `assistantsStore` state (`pinnedAssistants`,
   `helpAssistants`, `helpAssistantsFetched`) that `NavigationPinnedSection` already reads, so no
   new prop, context, or store is introduced, and the two components cannot disagree about whether
   there's content to reserve space for.

   When the floor is active (items present) and the section is squeezed below it, the section
   stops shrinking and the *header* overflows instead — which is now scrollable per change 1 — so
   the deficit becomes "scroll to see more" rather than "silently render nothing." This also means
   `NavigationPinnedSection`'s own `computeCollapsedBubbles`/`computeExpandedBubbles` logic
   (unchanged) will always have enough `availableHeight` to show at least one bubble plus its own
   overflow affordance, instead of collapsing to zero items. When there are zero items, the
   wrapper takes zero height exactly as it does today, so no space is wasted in the tight-viewport
   case this ticket is about.

No other structural change to `Navigation.tsx` is needed — the two `flex-1 min-h-0` wrappers
above the pinned section's own (`Navigation.tsx:228-229`) can keep plain `min-h-0`; only the
innermost wrapper (line 230, directly sized to the component it contains) needs the conditional
floor, since it is the one wrapper whose min-content size is genuinely zero (an empty state is
valid) and therefore the one place the shrink algorithm has nothing else stopping it.

### Secondary checks required by this approach (verification items, not open decisions)

- `NavigationProfile`'s `OverlayPanel` repositions on `window.resize` but not on container scroll
  (`NavigationProfile.tsx` ~lines 57–71). Verify the popup does not visually detach from its trigger
  button once the trigger can move via scroll instead of resize — if it does, add a scroll-aware
  reposition (e.g. an `onScroll` listener on the new scroll container calling the same reposition
  logic already used for resize). Only add this if detachment is actually observed.
- `react-tooltip` anchors on collapsed nav items (e.g. on `NavigationExpandButton`, and on the
  pinned-section bubbles themselves) must not clip or mis-anchor inside the new overflow boundary.
  `overflow-x-hidden` is the standard mitigation already used elsewhere; visually confirm tooltips
  still render correctly once scrolled.
- Confirm the new height floor on the pinned-section wrapper does not itself force the header to
  overflow (and thus show a scrollbar) in the common case where everything already fit — the floor
  should only change behavior once content genuinely exceeds viewport height.
- Confirm the zero-items case (no pinned assistants, no help assistants fetched yet or empty)
  renders with zero height contributed by this wrapper, matching `NavigationPinnedSection`'s
  existing empty-state render guard, so no space is reserved when there is nothing to show.

## Acceptance criteria

- The desktop branch of `#navigation-menu` scrolls vertically (via native `overflow-y-auto`) when
  its content height exceeds the available viewport height.
- At reduced viewport heights, every nav item — including Help, Profile, and the Hide Menu/Show
  Menu toggle — is reachable by scrolling, without changing browser zoom.
- At reduced viewport heights, when the pinned-assistants section has at least one item (including
  FAQ and Chatbot), it remains visible with at least one bubble and, if needed, its overflow
  affordance — it must never render as fully empty/hidden the way it does today; any further
  pinned items it cannot show become reachable via its existing overflow dropdown or via scrolling
  the header, not by disappearing.
- When the pinned-assistants section has zero items to show, it contributes no reserved height —
  the fix must not waste vertical space in the tight-viewport case by reserving a floor for
  content that isn't there.
- Scrolling works via mouse wheel, touchpad, and keyboard (native overflow scrolling satisfies all
  three with no custom JS, consistent with every other scroll region in this codebase).
- Nav items remain clickable/selectable and visually correct (no clipped text, no mis-positioned
  tooltips or popups) while the nav is scrolled to any position.
- `appInfoStore.navigationExpanded`/`sidebarExpanded` driven expand/collapse, width changes, and
  resizing continue to work unchanged; `data-app-content` main-area scrolling is unaffected.
- The mobile branch (`isMobileLayout` true arm) is untouched and continues to behave as today.
- `Navigation.test.tsx` gains at least one assertion that the desktop header carries the expected
  overflow classes (class-presence check — jsdom does not model real pixel overflow, this is a known
  limitation, not a gap to engineer around).

## Non-goals

- No change to `NavigationPinnedSection`'s internal `computeCollapsedBubbles`/`computeExpandedBubbles`
  bubble-selection logic — only the conditional height floor feeding its `ResizeObserver` changes.
- No new prop, context, or store — `Navigation.tsx` reads the existing `assistantsStore` state the
  child component already reads, rather than introducing a new signal between them.
- No change to `appInfoStore`, routing, or any other API/data layer — this is a Tailwind class
  change on the header, a conditional height-floor change on one existing wrapper driven by
  already-available store state, plus the secondary verification checks above.
- No custom scrollbar styling/component — plain native `overflow-y-auto`, consistent with the rest
  of the codebase.
- No pixel-perfect/visual-regression test harness for scroll behavior; coverage stays at the
  class-presence level already used by `Navigation.test.tsx`.
- No change to the mobile overlay branch, which already works correctly.
- Profile and Hide Menu are explicitly **not** pinned/docked at the bottom of the sidebar — they
  scroll with the rest of the content (Option A, chosen over a non-scrolling-footer sandwich).

## Open risks

- `OverlayPanel` scroll-reposition behavior is unverified until implementation; may require a small
  scroll listener if detachment is observed (see Secondary checks above).
- The exact floor value for the pinned-section wrapper is derived from existing constants
  (`ITEM_HEIGHT`, `CONTAINER_PB`) but has not been visually verified against real padding/gap
  composition at implementation time; the plan/implementation stage should confirm the floor
  actually yields one visible bubble row rather than a partially-clipped one.
- Reading `assistantsStore` from both `Navigation.tsx` and `NavigationPinnedSection.tsx` duplicates
  a derived condition (`helpAssistantsFetched && allItems.length > 0`) across two components; this
  is accepted here as the smallest change that keeps the floor and the render decision from
  disagreeing, without adding new plumbing — worth a code-review glance at implementation time, not
  a blocking concern.
- jsdom-based tests cannot simulate real pixel overflow, so the automated regression net for this
  fix is necessarily class-presence-based; manual verification across the listed browser/viewport
  matrix in the ticket's AC remains required.
