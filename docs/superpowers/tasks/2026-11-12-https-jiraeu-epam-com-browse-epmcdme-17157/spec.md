# EPMCDME-17157 — Let hosted apps use their own Full screen and Focus controls

## Problem

A hosted HTML deck has its own presentation toolbar (Nav, Laser, Focus, Timer, Full, Light). In the CodeMie viewer, two of those controls fail. The user confirmed this on their real deck in the preview viewer:

- **Full** does nothing. The browser denies the Fullscreen API at both iframe layers. The inner content frame sets `fullscreen 'none'` (`src/utils/hostedApplicationFrame.ts:59`). The outer srcdoc viewer iframe (`src/pages/applications/hosted/HostedApplicationViewer.tsx:329-333`, sandbox `allow-scripts allow-same-origin`) has no fullscreen permission.
- **Focus** shows the deck's message "Pop-up blocked. Allow pop-ups to open Focus view." This happens because neither sandbox includes `allow-popups`.

This branch also adds CodeMie-level "Full screen" and "Focus mode" viewer buttons (commits 3792b09a7, 97941a20b, 296f26942, 3a3599c57 on top of 4266f47c0). They do not fix the deck's own controls, and they are withdrawn.

## Approach

The fix makes the hosted app's own controls work by granting exactly two capabilities to the hosted content. Nothing else changes.

- **Inner content frame** (`createHostedFrame`, `hostedApplicationFrame.ts:59`): in the `allow` list, replace `fullscreen 'none'` with a fullscreen grant scoped to the content origin, which `SAFE_ORIGIN` already validates. Add `allow-popups` to its sandbox.
- **Outer viewer iframe** (`HostedApplicationViewer.tsx:329-333`): add a fullscreen permission (`allow="fullscreen"` / `allowFullScreen`) so the grant can pass down to the inner frame. Add `allow-popups` to its sandbox. Sandbox flags intersect down the frame tree, so the inner frame's `allow-popups` only takes effect when the outer frame has it too.
- **Popups stay sandboxed.** `allow-popups-to-escape-sandbox` is not added, so a popup opened by the deck inherits the frame's sandbox.
- **Withdraw the viewer-level controls.** Remove `useHostedPresentation`, the Full screen / Focus mode buttons in `HostedViewerActions`, their wiring and the focus-mode inert logic in `HostedApplicationViewer`, and the tests for all of these. Compared with 4266f47c0, the branch's net diff then contains only the frame-permission change and its tests.
- **Standalone / "Open in new tab" path:** no change. It does not use `createHostedFrame` and builds no iframe. `openHostedLaunchWindow` opens a top-level tab, and `submitHostedLaunch` posts the ticket by form to that tab or to `_self` (`src/utils/hostedApplicationLaunch.ts:73-88`, `HostedStandaloneLaunch.tsx:47`). The content there is top-level, so no iframe policy applies to it.

## Acceptance criteria

1. In the viewer (view and preview routes), clicking the deck's own **Full** control puts the deck into browser full screen, so only the deck is shown (ticket AC1, AC3).
2. Leaving full screen (Esc, the browser's exit, or the deck's own toggle) returns to the regular viewer, and the deck stays on the same slide (ticket AC4).
3. In the viewer, clicking the deck's own **Focus** control opens the deck's Focus view in a new window. The "Pop-up blocked" message does not appear (ticket AC2, AC3).
4. Closing the Focus window, or using the deck's own exit, leaves the viewer as it was (ticket AC4).
5. Access control is not weakened (ticket AC5). The frames' `allow` lists keep camera, microphone, geolocation, payment and usb at `'none'`. Fullscreen is granted only to the content origin on the inner frame. Each sandbox gains only `allow-popups`, and `allow-popups-to-escape-sandbox` is never added. The CSP, launch ticket, message source/origin checks (`HostedApplicationViewer.tsx` message listener) and origin isolation are unchanged.
6. No viewer-level presentation controls remain. The header has no "Full screen" or "Focus mode" button, no focus-mode layer or inert handling exists, and `useHostedPresentation` and its tests are gone.
7. Unit tests pin the new policy. `hostedApplicationFrame.test.ts:36` asserts the content-origin fullscreen grant instead of `fullscreen 'none'`, plus `allow-popups` on the inner sandbox and the absence of `allow-popups-to-escape-sandbox`. The viewer tests that pin the outer frame's sandbox and permissions (currently `HostedApplicationViewer.test.tsx:326-331` and `embedded-viewer.integration.test.tsx:314`) assert the new sandbox and the fullscreen permission.
8. Criteria 1–4 are verified in a real browser with a local test deck generated by the codemie-html-report skill, which has the same built-in Full and Focus controls. jsdom cannot run the Fullscreen API.

## Non-goals

- CodeMie-level presentation controls of any kind (a viewer full screen button, a focus mode layer, hiding page chrome).
- Adding `allow-popups-to-escape-sandbox`, `allow-top-navigation`, `allow-modals`, `allow-forms` or any other sandbox flag.
- Granting any other powerful feature (camera, microphone, geolocation, payment, usb).
- Changing the container CSP, the launch ticket flow or the postMessage protocol.
- Changing the standalone / "Open in new tab" launch path.
- Deck-specific features (presenter notes, slide navigation).
- Server-side `Permissions-Policy` headers (`nginx.conf` or the content host).

## Decisions

- Fix the hosted app's own Full and Focus controls over CodeMie viewer-level controls. This answers what "full screen and focus mode" in the ticket means. — user
- Grant fullscreen to the content origin on the inner frame, plus fullscreen on the outer frame, over keeping `fullscreen 'none'`. This answers how the deck's Full control can work. — user
- Add `allow-popups` to both sandboxes over leaving popups blocked. This answers how the deck's Focus view can open. — user
- Popups inherit the sandbox over `allow-popups-to-escape-sandbox`. This answers how much the popups may do. — user
- Remove the viewer Full screen / Focus mode buttons, hook and inert logic already built on this branch over keeping them alongside. This answers whether the branch keeps viewer-level controls. — user
- Security rationale, signed off under ticket AC5: a hosted app may now go full screen and open popups, and only after a user gesture, because browsers require one. Those popups stay sandboxed on the content origin. Access is still decided by the launch ticket, origin isolation and message checks, none of which change, so this widens what an app can display, not who can open it. — user
- Leave the standalone / "Open in new tab" path untouched over applying the same grants there. It builds no frame with `createHostedFrame`, and top-level content needs no grant. This answers the user's request to check consistency.
- Verify in a real browser with a codemie-html-report test deck over unit tests alone. This answers how the Fullscreen and popup behaviour gets verified.

## Assumptions and risks

- Assumption: the deck's Focus view works inside a popup that inherits the sandbox (`allow-scripts allow-same-origin allow-popups`). If it needs a flag outside that set, criterion 3 fails in browser verification and the gap goes back to the user. It is not widened silently.
- In full screen, publisher content fills the screen without CodeMie's "content provided by its publisher" label. The browser's full-screen notice names the CodeMie origin. This is accepted under the rationale above: full screen needs a user gesture, and Esc always exits.
- The content host may send its own `Permissions-Policy` header that blocks fullscreen (unverified, outside this repo). Browser verification against the real content host would show it.
