# Technical Analysis: EPMCDME-10928 — Configurable Integration URL Defaults (UI)

## Task

Fetch `GET /v1/tools/configs` at startup and use the backend-provided URL placeholders to override the hardcoded `defaultUrl` values in `settingsUIConfig.ts`, making integration URL defaults deployment-configurable.

---

## Codebase Findings

### Current defaultUrl flow

`src/utils/settingsUIConfig.ts` exports `CREDENTIAL_UI_MAPPING` — a static module-level object where every integration type has a hardcoded `defaultUrl` (e.g. `jira: { defaultUrl: 'https://jira.example.com/' }`).

Two functions in `src/utils/settings.ts` consume it:

- `getDefaultUrl(credentialType)` — returns `CREDENTIAL_UI_MAPPING[type].defaultUrl ?? 'AutoGenerated'`
- `getSettingCredsURL(credentialValues, credentialType)` — returns stored URL or `getDefaultUrl()`

These are the only call-sites that need changing. `CREDENTIAL_UI_MAPPING` itself stays static (fallback layer).

### Startup data fetching

`src/hooks/appLevel/useInitialDataFetch.tsx` is the single place all app-level data is loaded. It calls `appInfoStore.fetchCustomerConfig()`, `appInfoStore.getLLMModels()`, etc. Adding `appInfoStore.fetchToolConfigs()` here is the prescribed pattern.

### `appInfoStore` (`src/store/appInfo.ts`)

Valtio proxy with typed methods following the pattern: `api.get('v1/...')` → `response.json()` → store property. No existing `v1/tools/configs` call. Adding `toolUrlDefaults: Record<string, string>` and `fetchToolConfigs()` here is consistent with the existing shape.

### `v1/tools/configs` response format

Array of single-key objects. Key = lowercase class name (e.g. `"jiraconfig"`). Value = config schema with fields. Each URL field has a `placeholder` property:

```json
[
  {
    "jiraconfig": {
      "class": "...",
      "credential_type": { "default": "Jira", ... },
      "url": { "placeholder": "https://jira.example.com/", "type": "string", ... }
    }
  }
]
```

Two configs use `base_url` instead of `url`: `keycloakconfig` and `xrayconfig`.

### Backend → UI credential type mapping

Multiple backend config classes can share the same `credential_type.default` (e.g. `gitlabconfig` and `githubconfig` both use `"Git"`). To avoid ambiguity, the mapping is indexed by config class name (not `credential_type.default`).

The relevant 15 configs and their URL fields:

| Backend config key | UI credential type | URL field |
|---|---|---|
| `jiraconfig` | `jira` | `url` |
| `confluenceconfig` | `confluence` | `url` |
| `gitlabconfig` | `git` | `url` |
| `keycloakconfig` | `keycloak` | `base_url` |
| `azuredevopsgitconfig` | `azuredevops` | `url` |
| `elasticconfig` | `elastic` | `url` |
| `emailtoolconfig` | `email` | `url` |
| `sonarconfig` | `sonar` | `url` |
| `xrayconfig` | `xray` | `base_url` |
| `zephyrconfig` | `zephyrscale` | `url` |
| `servicenowconfig` | `servicenow` | `url` |
| `reportportalconfig` | `reportportal` | `url` |
| `kubernetesconfig` | `kubernetes` | `url` |
| `sharepointconfig` | `sharepoint` | `url` |
| `xwikiconfig` | `xwiki` | `url` |

`githubconfig` is intentionally excluded — `git.defaultUrl` represents the GitLab URL.

### Mock server

`mock-server/routes.json` maps URL patterns to `db.json` keys. The `v1/tools/configs` route is absent — needs adding.

## Risk Indicators

- **Low blast radius**: changes are additive. `CREDENTIAL_UI_MAPPING` stays unchanged; `toolUrlDefaults` is empty on fetch failure, so fallback to hardcoded values always works.
- **No circular dependency risk**: `appInfoStore.ts` already depends on `api.ts`. `settings.ts` already imports `appInfoStore` (indirectly through other stores).
- **Ordering**: `fetchToolConfigs()` is fire-and-forget (no `await` in `useInitialDataFetch`). The settings page isn't visible until after startup completes, so the data will be present before users interact with integrations.
- **Type safety**: The response is `Array<Record<string, Record<string, unknown>>>` — accessed defensively with optional chaining.
