An `authenticating` row untracked by `clearRows`, a chat switch, or a cancel therefore keeps a live 600s timer that later fires `onIdAcceptanceExpiry` and sends a `result: 'timeout'` beacon for a flow the user abandoned — behaviour the pre-change code did not produce, since untracking cleared the only timer.
- AC 7 ("exactly one diagnostics beacon per id") is contradicted on the retry path: after a hint expiry the id is untracked with its acceptance handle still in `acceptanceTimeoutsRef`, and re-tracking overwrites that map entry without `clearTimeout` — `src/hooks/useAuthCallbackListener.ts:239-242`. Both timers stay armed and each calls `reportCallbackTimeoutDiagnostics`, which has no per-id dedupe guard (`:125-155`), so one id yields two beacons.
- AC 1 is only partially met for a retried sign-in: the leaked first-attempt acceptance timer runs `retainedIdsRef.current.delete(authConfigId)` at its own deadline (`src/hooks/useAuthCallbackListener.ts:206-207`), purging retention while the retried flow's PKCE lifetime and its own acceptance window are still open, so a callback arriving in that gap is dropped by the id gate at `:291-300`.
